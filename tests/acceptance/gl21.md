These acceptance targets cover the full pinned compatibility API; a CPU frontend

- [Requirement map](#gl21.spec-catalog), [fixed function](#gl21.legacy-pipeline) and [additional features](#gl21.extended-graphics)
- [Advertised extensions](#gl21.extensions)

The [fixed-function](../../spec/cases/gl21.fixed-function.json) and
[extra-feature](../../spec/cases/gl21.extra-features.json) lists define the cases
and piglit name patterns that prove them. The conformance family is piglit's
GL ≤ 2.1 selection, pinned by the [local metadata](../../spec/cases/gl21.external-conformance.json)
(7,093 tests). Feature and
extension cases are derived from those results: a case passes when every piglit test matching
its patterns passes, and a case whose patterns match no test fails, because a feature without a
test is not covered.

Mesa core's own software paths (selection, feedback and the accumulation buffer) are shared by
every Gallium driver. They are listed as fixed-function cases with that path, not as driver
fallbacks.

applicable tests. Apply the per-resource limit-boundary method referenced in the metadata to

## Every extension EMGD advertised

<a id="gl21.advertised-extensions"></a>

### gl21.advertised-extensions

Procedure: Compare the M1 build's `glxinfo` with EMGD 1.8's 70 GL extensions and
EXT_texture_sRGB, and run each extension's piglit tests.

Oracle: Each listed extension is advertised and every piglit test matching its patterns passes on
the GPU path. Not advertising one needs an exclusion a maintainer accepts, with independent
evidence: Mesa 26.2.4 has no entry for ARB_matrix_palette, ARB_shadow_ambient, ARB_vertex_blend
or IMG_texture_compression_pvrtc. An extension no test of the selection targets stays open until
a test exists. An extension we advertise that EMGD did not needs its own case before it ships.

<a id="gl21.window-system"></a>

## Window-system configs: EGL on X11 and GLX

<a id="gl21.wsi-configs"></a>

### gl21.wsi-configs

Procedure: List the EGL configs of the X11 platform and the GLX fbconfigs and visuals on our DDX
(`eglinfo`, `glxinfo -v`, a raw xcb-glx probe of the server list), then render in each config the
cases name: RGBA8 with D24S8, RGB565 with depth 16, 4 samples, the root and ARGB visuals, and a
direct context on every offered visual.

Distinguish server-advertised configs from those the Mesa client can use. Our DDX has no DRI2,
so Xorg's GLX uses the DRISWRAST provider's server config list; this does not establish the
client's renderer or supported render formats. Check colour, depth/stencil and sample count
against the [current screen admission](../../docs/graphics.md#screen-admission), then verify
the complete config on the GPU. Depth-16/RGB565 and multisample cases remain required even
when the current driver refuses them.

Oracle: Each config exists, is direct, reports GL_RENDERER poulsback and renders exactly on the
GPU path; a config backed by swrast or llvmpipe fails.

<a id="gl21.glx-tfp"></a>

### gl21.glx-tfp

Procedure: Bind X pixmaps as textures (`GLX_EXT_texture_from_pixmap`, EGL native pixmap images),
rebind after X draws, and render into small GLX pixmaps and pbuffers.

Oracle: Each sample reads the pixmap's current colour. Today a pixmap without a BO (under 4096
pixels, or a depth other than 24 or 32) gets BadPixmap from DRI3's BuffersFromPixmap; those cases
stay open until the DDX gives every exported pixmap a BO.

<a id="gl21.wsi-software-detect"></a>

### gl21.wsi-software-detect

Procedure: Try indirect and software contexts, and inspect what a GL test process maps.

Oracle: Indirect and software contexts are refused or detected; no GL suite passes on llvmpipe,
an indirect context or Debian's Mesa libraries.

## GLX/DRI3 contexts, sharing and presentation

<a id="gl21.glx-contexts"></a>

### gl21.glx-contexts

Procedure: Create compatibility GL contexts through GLX/DRI3, render/swap and test
sharing/teardown on X11.

Oracle: GLX/DRI3 promised interfaces work with correct fences, framebuffer contents and
lifetime; renderer identity proves selected driver.

Reuse the shared-resource concurrency cells identified in the metadata, through the selected GLX
path. Check observable GLX/GL error and context-loss behavior for that profile. Do not require
an unadvertised robustness extension or substitute an EGL result for a GLX client result.
