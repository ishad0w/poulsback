# Architecture

poulsback separates the hardware engines from the operating-system interfaces
and from the tools used to establish correctness.

Linux provides the existing display/KMS infrastructure. Kernel components add
bounded ownership, buffers, translation/cache handoff, job state and diagnostics.
Command builders and compiler libraries construct and validate fields on the
CPU. Mesa may shade vertices on the CPU when the vertex backend refuses a draw;
rasterization and fragments execute on the GPU.

## Repository layout

The repository contains an external Linux DRM module, Mesa integration and
shared CPU libraries. It is not a Linux source-tree checkout. The kernel builder
prepares a separate source directory and invokes the kernel's
[external-module Kbuild interface](https://docs.kernel.org/kbuild/modules.html).
Mesa integration is an overlay against its locked source version.

| Path | Contents |
| --- | --- |
| `kernel/` | Linux implementation and integration patch; the module build is generated by `tools/build-kernel.py` |
| `include/uapi/poulsback/` | Versioned interfaces shared by kernel and userspace |
| `src/compiler/` | Shader backends, NIR adapters and instruction/PDS codecs; only selected helpers also build in the kernel |
| `src/raster/` | Pure geometry, packet and raster-state construction |
| `src/gallium/` | Mesa overlay, driver-local tests and graphics dependency lock |
| `src/xorg/` | Xorg DDX: KMS, EXA/fb, DRI3 and Present |
| `support/` | [Data-only build targets](building.md#build-targets-and-compatibility); no duplicated driver or execution admission |
| `src/video/` | Video descriptors, firmware/message planners and CPU transport model |
| `tests/` | [CPU suites, fixtures and project checks](../tests/README.md) |
| `tools/` | [Source restoration, builders, checkers and development utilities](tools.md) |
| `spec/` | Machine-readable acceptance parameters, scopes, artifacts and dependencies; not compiled driver code |
| `docs/` | Component contracts, build recipes and verification methods |
| `docs/re/` | Legacy implementation mechanisms, source identities and unresolved hardware joins |

`spec/` stays at the project root because both kernel and userspace checks use
its contracts. `tests/kernel/` contains host tests and mocks of kernel
components. Gallium
tests beside its Meson file use the same Mesa internal ABI as the overlay.
Build outputs and restored external sources stay outside the tracked source tree.

## Component boundaries

The kernel separates job submission (validated in the ioctl), scheduling and
fences, execution on the engine and cached observations (debugfs and the
`debug` log). The [execution owner](kernel/execution.md)
defines their interfaces and CPU custody; the [memory owner](kernel/memory.md)
defines mapping, cache and resource retirement. The
[display owner](kernel/display.md) defines independent display use and release.
Failure after possible publication preserves the original owners; cleanup
errors remain separate from the initiating error.

SGX535 compiler modules own instruction codecs and lowering. Mesa/Gallium owns
resources, state tracking, textures, render targets and shader-stage interfaces;
the winsys connects those resources to DRM objects and fences.

The [graphics integration owner](graphics.md#frame-path) defines the frame path
and available interfaces. The vertex backend executes accepted shaders on the
USSE; Mesa `draw` retains vertex transformation and lighting for its fallback.
GPU-shaded draws can use
the fragment backend with per-draw depth/stencil/offset, blend and output state; the
fallback retains the bounded COLOR0 fragment limits. Hardware graphics requires SGX
rasterization and fragment processing, plus depth where the scene uses it.
Readback is a diagnostic oracle; presentation flips buffer objects or copies
them on the 2D core. Each scene qualifies only its own operations.

One DRM device serves display and rendering. A buffer object owns its physical
storage and reservation object; a `SCANOUT` BO is also a KMS framebuffer, and its
display GTT binding and SGX address-space mappings have separate ownership and
retirement ([display](kernel/display.md#typed-display-lifetime-foundation)).
Static SetCrtc output does not qualify continuous presentation (page flips).
Per-file handles do not grant access to another client's buffers or executable
state. Render-node
exposure requires validated submissions and qualified isolation, rather than
merely assigning a render-allowed flag to a diagnostic ioctl.

MSVDX is a separate engine. Its CPU helpers normalize descriptors, construct
messages, qualify relocation spans and plan ring placement. Firmware pairing,
MMU ownership, submission, completion and decoded surfaces are separate work.

Wayland and API feasibility constraints belong to the graphics
[research profiles](graphics.md#research-profiles).

### Kernel compilation boundaries

Each kernel component is its own object (`MODULE_OBJECTS` in
`tools/build-kernel.py`): the engine, contexts, `SUBMIT` and its register table,
the 2D planner and encoder, BOs, address spaces and their layout, the display
domain, framebuffers, the display GTT and the selected PSB source, diagnostics,
the source epoch and the engine's IRQ route. The selected display provider
compiles in `poulsback_display_psb_source.c`; a narrow integration leaf
identifies legacy framebuffers beside Linux's private framebuffer table. The GTT
reservation, GEM hold, foreign-MMU and SGX-root leaves are `.inc` files compiled
inside the patched upstream files that own their private state.

There is one build; no compile-time profile selects a composition. The
[execution](kernel/execution.md), [memory](kernel/memory.md),
[display](kernel/display.md) and [diagnostics](kernel/diagnostics.md) owners
define the externally callable interfaces and their retained references.

## GPU hardware contracts

The [GPU hardware reference](hardware.md) owns shared facts about address units,
USE/PDS linkage, translation/cache domains, engine events and firmware handoff.
It distinguishes checked source contracts, finite device observations, software
policy and unresolved behavior. Component guides link to those contracts and
own their implementation interfaces. The [legacy implementation reference](re/README.md)
explains the producer/consumer chains behind those facts, with
[source profiles](re/sources.md) and [address conventions](re/address-domains.md).

## Result scopes

Every result identifies its source, build, device/profile and scope:

| Scope | What it checks |
| --- | --- |
| BUILD | The selected sources/dependencies compiled for the recorded ABI; no test, kernel runtime or device result is implied. |
| CPU | Executed encoding, validation, models or userspace fixtures; no physical GPU execution. |
| KERNEL RUNTIME TESTED | Executed code in an identified Linux kernel/runtime, separate from CPU models, compile-only Kbuild and physical GPU work. |
| HARDWARE | A recorded operation on the identified device. State separately which outputs, visibility and lifetime conditions were checked. |
| PRESENTATION | Displayed frames, timing and display release through the identified path. |
| API-CONFORMANCE | The enumerated mandatory behavior of a pinned API and test selection. |

Saved captures qualify only their recorded configuration and checked conditions.
A HARDWARE result may establish an image while retaining resources in HOLD; it
does not imply successful retirement. Performance is measured separately; a
correct image or passing API call does not establish a frame rate.

## Terms

Component guides use these terms for resource and job handling:

| Term | Meaning |
| --- | --- |
| Owner | Driver object that retains a resource, its identity and its release rules. |
| Canonical object | The authoritative object retained by the driver; copying its fields does not copy its authority. |
| Lease | A held reference permitting a specific use of a resource within one source epoch. |
| Source epoch | A generation identifying the device state used to prepare a job. Reset or source loss invalidates that generation. |
| Publication | An action that can make mappings or work visible to the device. Once it may have happened, ordinary rollback is insufficient. |
| Completion | A result associated with a particular job. Resource release also requires retirement and any display release. |
| CPU payload release | Disposal of copied input or preparation references after another owner has taken the required custody. It does not imply queued cancellation, GPU retirement or display release. |
| Worker action | Whether queue processing continues or stops with retained state. It is separate from the job's error, fence and device-completion observations. |
| Retirement | Proof that the job can no longer use its resources, including the required device drains and mapping/cache retirement. |
| HOLD | Retain uncertain resources and their references until the documented recovery or release condition is established. |
| Qualified | Validated for the recorded source, build, profile and test scope. |
| Winsys | Gallium's interface to DRM buffers, device identity and synchronization. |

## Interface boundaries

- Public UAPI uses typed fields and per-client handles; internal GPU addresses
  and register writes are not arbitrary caller inputs.
- CPU upload/download must agree with the GPU mapping and cache attributes.
- Once device publication is possible, failure cannot prove no work occurred.
  Resources remain held until retirement or qualified recovery.
- Debug observations must not create device work or change lifetime decisions.
- Building and CPU checks do not submit GPU work or change a boot configuration.
